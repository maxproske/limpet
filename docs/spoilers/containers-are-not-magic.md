# Errata: "Containers Are Not Magic" (Parts 1–2) and its repo

> **Spoiler. Don't read until you've finished P7 and reviewed the series yourself.** This is the answer key for that review. Reading it first would turn the exercise into recall.

Compiled 2026-10-13 and checked against the man pages, kernel docs, and the Go 1.27.2 source. Quotations from the series are abbreviated.

## Part 1: namespaces

1. **"Namespace creation needs root."** That's only true because the code never creates a user namespace. Since Linux 3.8, unprivileged processes can create user namespaces, and inside one they can create the other kinds. In Go, that's `CLONE_NEWUSER` plus `UidMappings`/`GidMappings`. Sources: [user_namespaces(7)](https://man7.org/linux/man-pages/man7/user_namespaces.7.html), [`SysProcAttr`](https://pkg.go.dev/syscall#SysProcAttr).
2. **"Go doesn't use fork(); it starts a fresh process with exec."** Wrong. Go's `forkExec` calls `clone` with your `Cloneflags` (plus `CLONE_VFORK|CLONE_VM` when no user namespace is requested), runs only raw syscalls in the child, then calls `execve`. The re-exec trick exists because no *Go code* can run between the clone and the exec. Source: `src/syscall/exec_linux.go`, line 309 in Go 1.27.2.
3. **"/proc/self/exe prevents spoofing and argument injection."** It's just a reliable path to the running binary, not a security control. The same mechanism was the root of runc's CVE-2019-5736, where a container overwrote the host's runc binary. Sources: [proc_pid_exe(5)](https://man7.org/linux/man-pages/man5/proc_pid_exe.5.html), [CVE-2019-5736](https://nvd.nist.gov/vuln/detail/CVE-2019-5736).
4. **"Pdeathsig sends SIGTERM if the parent dies, so no orphans."** This fails in two ways.
   - The signal is tied to the *thread* that created the child, which can exit before the process does. Go's documentation says so explicitly (go.dev/issue/27505).
   - The child is PID 1 of a new PID namespace, and SIGTERM from outside is dropped unless that init has installed a handler. Use SIGKILL.
   Sources: [`SysProcAttr`](https://pkg.go.dev/syscall#SysProcAttr), [pid_namespaces(7)](https://man7.org/linux/man-pages/man7/pid_namespaces.7.html).
5. **"Setsid keeps the shell from getting confused."** It's the other way round. `setsid` creates a session with *no* controlling terminal, which is exactly why the post's own screenshot shows `can't access tty; job control turned off`. The fix is `Setctty`/`Ctty` (TIOCSCTTY) or a PTY, which is P8's subject. Source: [setsid(2)](https://man7.org/linux/man-pages/man2/setsid.2.html).
6. **"MS_NODEV: no sneaking into /dev/sda" and "filesystem isolation confirmed".** Those flags apply only to the new procfs mount. With no new root and full capabilities, the host's `/dev` and filesystem are still reachable. Seeing a new `/proc` doesn't prove filesystem isolation. Source: [mount(2)](https://man7.org/linux/man-pages/man2/mount.2.html).
7. **"Hardening just like Docker."** Docker's real protections are dropped capabilities, seccomp, and masked or read-only `/proc` paths, and none of them is present here. This shell is effectively `--privileged`, with a writable `/proc/sys`, so writing `core_pattern` would be a host escape. Sources: [Docker: runtime privilege and Linux capabilities](https://docs.docker.com/engine/containers/run/#runtime-privilege-and-linux-capabilities), [core(5)](https://man7.org/linux/man-pages/man5/core.5.html).

Part 1 gets these right: `MS_REC|MS_PRIVATE` on `/` before mounting proc (Go does this automatically only for `Unshareflags`, not `Cloneflags`), mounting procfs from inside the new PID namespace, and avoiding in-process `setns`/`unshare`.

## Part 2: cgroups and chroot

1. **"chroot can never be escaped."** `cd ..` at the new root was never the escape. The documented ones are chrooting into a subdirectory without changing the working directory, or using a file descriptor opened outside the root, and a root process with `CAP_SYS_CHROOT` can do either. chroot "is not intended to be used for any kind of security purpose"; runtimes use `pivot_root` in a mount namespace. Sources: [chroot(2)](https://man7.org/linux/man-pages/man2/chroot.2.html), [pivot_root(2)](https://man7.org/linux/man-pages/man2/pivot_root.2.html).
2. **"Namespaces only isolate in-memory resources, not files on disk."** Mount namespaces isolate the mount list, and combined with `pivot_root` that's exactly how runtimes restrict the filesystem. Source: [mount_namespaces(7)](https://man7.org/linux/man-pages/man7/mount_namespaces.7.html).
3. **"The deferred cleanup always runs."** `os.Exit` skips deferred functions, so every error path leaks the cgroup. `rmdir` on a cgroup also fails while it still has live processes, and the code ignores that error. Teardown should kill the processes first (`cgroup.kill`) and check errors. Sources: [`os.Exit`](https://pkg.go.dev/os#Exit), [cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html).
4. **"cmd.Start() gives a window to move the PID into the cgroup before it does anything."** There's no such window. `Start` returns only after the child has already exec'd the target, so the workload runs unconfined until it's moved. The race-free method is `SysProcAttr.UseCgroupFD`/`CgroupFD`, which uses clone3 with `CLONE_INTO_CGROUP` (Linux 5.7+). The aside about runc is also wrong: runc's C `nsexec` handles namespaces, and cgroups are applied by its Go parent before the child is released. Sources: `src/syscall/exec_unix.go` (`forkExec` reads the exec status from a pipe), [clone(2)](https://man7.org/linux/man-pages/man2/clone.2.html).
5. **"The shell survived the OOM because it's PID 1."** Only the global init is exempt from the OOM killer. A namespace's PID 1 isn't, and victims are chosen mainly by memory use. `memory.oom.group` kills a container as a unit. Sources: [proc_pid_oom_score(5)](https://man7.org/linux/man-pages/man5/proc_pid_oom_score.5.html), [cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html).
6. **"137 is Linux's exit code for SIGKILL."** A process killed by a signal has no exit code. `wait` reports the signal, and 128 + 9 is a convention used by shells (and Docker) when reporting it. Go's `ProcessState.ExitCode()` returns -1 in that case, which matters for P3. Sources: [wait(2)](https://man7.org/linux/man-pages/man2/wait.2.html), [`os.ProcessState.ExitCode`](https://pkg.go.dev/os#ProcessState.ExitCode).
7. **"The kernel populates the new directory with all the control files."** Only the files for controllers enabled in the parent's `cgroup.subtree_control` appear, and the code never enables `+memory +pids`. The tip to look for `docker-*` directories is also off for cgroup v2: with the systemd driver, Docker uses `system.slice/docker-<id>.scope`. Sources: [cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html), [Docker runtime metrics](https://docs.docker.com/engine/containers/runmetrics/#find-the-cgroup-for-a-given-container).
8. **The cgroup documentation links point at kernel v4.18**, which predates `memory.oom.group`, `cgroup.kill`, and `cgroup.freeze`.
9. **"Equivalent to `docker run --memory=50m`" and "exactly what runc does".** It isn't equivalent: Docker drops capabilities, applies seccomp, and uses `pivot_root`. This runtime is closer to `--privileged`.

## The repo

1. **The child is detected by scanning every argument for "child".** A flag *value* of `child` (say `--name child`) runs the child code path in the host's namespaces. That sets the host's hostname, changes the host's mount propagation, and mounts proc in the host namespace, then crashes on `args[i+1]`. The error from `syscall.Exec` is also discarded.
2. **`setup.sh` hard-codes an x86-64 Alpine 3.19 root filesystem.** Alpine 3.19 reached end of life in November 2025, the script doesn't verify the published checksum, and the binaries fail with ENOEXEC on arm64. Source: [Alpine releases](https://alpinelinux.org/releases/).
